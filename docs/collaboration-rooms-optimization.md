# 协作房间优化方案

本文基于实际使用中暴露的问题，给出分层优化方案。每一条都标了「为什么」和「代价」，
便于按需取舍。范围限制：不引入新的执行引擎，仍然复用每成员自己的会话。

---

## 一、现状诊断：为什么"不够智能"

不是模型不行，是**房间层缺少三个东西**：任务结构、角色分工、反馈闭环。

| 现象（实测） | 根因 | 影响 |
|---|---|---|
| `@Codex 刚才 Claude 的建议原话是什么` → Codex 逐字复述 | 派发只给自由文本，没有"这是一个任务"的结构 | 被指派方不知道要**做什么**，只能复述 |
| 时间线全是散文 | 成员输出是自由文本，房间不解析 | 人要在长文里找结论；无法驱动 UI 卡片 |
| 执行完就算了 | 没有验证回合 | "照着做"是否做对，全靠人肉检查 |
| 失败就是一行红字 | 无自动重试，无分类 | 一次抖动就要手动重发 |
| 成员状态只有 `空闲/处理中` | 运行时状态只在内存，且无原因字段 | 重启后界面说谎；排队时不知道为什么排 |
| 工具调用、改了哪些文件只在成员会话里 | 房间不订阅成员事件 | 想看过程必须点「跳转会话」，房间像个黑盒 |
| 想"建议用 opus、执行用便宜模型"做不到 | 成员没有 model/effort 字段 | 成本与质量无法分开控制 |
| `@全体` = 同一句话发给 N 个人 | 无并行/顺序语义 | 每人独立作答，还要人自己对比 |

一句话：**现在是个聊天室，不是个协作台。** 缺的是工作流语义。

---

## 二、方案总览（四层）

```
L1 任务结构     结构化产出 + 计划对象          ← 收益最大、成本最低
L2 角色与流转   成员角色、建议→执行→验证        ← 让"一个出主意一个干活"成为默认
L3 可观测性     成员回合轨迹、状态持久化、重试   ← 消除黑盒
L4 成本与容量   成员级模型、上下文预算、并发策略  ← 控制 token 与费用
```

优先级：**L1 → L2 → L3 → L4**。L1 单独就能明显改善"看起来不智能"。

---

## L1 任务结构

### 1.1 结构化产出约定

派发时要求成员在结论处输出一个**受控 JSON 块**（不强制全文 JSON，避免模型跑偏）：

````
```cc-plan
{"summary": "一句话结论", "steps": ["步骤1", "步骤2"],
 "risks": ["风险1"], "needs": ["需要用户确认的点"]}
```
````

- 解析成功 → 时间线渲染成**卡片**（结论 / 步骤清单 / 风险），而不是一坨文字
- 解析失败 → 原样展示，并标记 `未结构化`（不报错、不重试）
- 存储：`RoomMessage` 增加 `plan: Optional[dict]`，与 `text` 并存

**为什么**：这是"看起来智能"的最大杠杆 —— 同样是模型输出，有结构就能驱动 UI，
人一眼看到结论和步骤，而不是读 15 行散文。

**代价**：每个回合多 ~30 token 的输出；解析逻辑要容忍模型不遵守格式。

### 1.2 房间级计划对象

`Room.plan`：当前生效的计划，来自某个成员的 `cc-plan`。

```
plan = { source_member, created_at, steps: [{id, text, status, owner}] }
```

- 计划卡片上每个步骤可勾选/指派给某成员
- 指派某步骤 = 用该步骤文本派发给它（自动 `@`）
- 状态：`pending / running / done / failed`，由执行回合回填

**为什么**：把"建议"从一段话变成**可执行的清单**，这是"一个给建议、另一个照着做"
真正落地的地方。执行方拿到的是"第 2 步：加集成测试"，不是一段散文。

**代价**：中等。需要步骤状态机 + 与派发的衔接。

## L2 角色与流转

### 2.1 成员角色

`RoomMember.role`：`advisor | executor | reviewer | observer`（默认 `executor`）。

| 角色 | 派发时的行为 |
|---|---|
| advisor | 提示词要求产出 `cc-plan`，不要求执行 |
| executor | 收到的是**计划/步骤**，要求逐步执行并回报状态 |
| reviewer | 收到「产出 + 原计划」，只做符合性检查，不改代码 |
| observer | 不派发，只读（用于留档某个会话） |

**为什么**：现在的 `@Claude` 和 `@Codex` 语义完全一样，只能靠人写清楚。
角色把它变成提示词里的硬约束。

**代价**：低。字段 + 提示词模板。

### 2.2 流转模式（room.mode）

| 模式 | 行为 | 适用 |
|---|---|---|
| `chat`（现状） | 谁被 @ 谁答 | 自由讨论 |
| `advise_execute` | advisor 出计划 → **人点「执行」** → executor 执行 → reviewer 检查 | 你描述的场景 |
| `parallel_review` | `@全体` = 各成员独立作答 + 汇总卡片（并排对比） | 选方案、评审 |
| `roundtable` | 顺序发言，每人看到前面所有人的结论 | 深度讨论 |

**关键设计：`advise_execute` 在"人点执行"处停下。**
不做全自动 agent 互聊 —— 两个 agent 会互相附和、无限延伸，token 会失控，
而且你无法在中间纠偏。人点是**刹车**，不是麻烦。

**代价**：中高。这是 L2 的主体工作量。

### 2.3 提示词模板化

把现在硬编码的前缀（`[房间 … · 目录 …]`）换成分角色模板：

```
executor:
  你是房间「{name}」的执行方。目录 {cwd}。
  顾问给出的计划：
  {plan}
  要求：逐步执行；每完成一步用 cc-plan 回报该步状态；不要改变计划范围。
```

**代价**：低。但需要真实跑几轮调措辞 —— 提示词质量决定效果。

## L3 可观测性

### 3.1 成员回合轨迹

订阅成员会话事件（`tool_use`、`delta`、`turn_end`），存**有界**轨迹：

```
RoomMessage.trace = {
  tools: [{name, count}],        # "读文件 ×2 · 命令 ×1"
  files_changed: [path...],
  tokens: {in, out},
  duration_ms,
}
```

房间消息下展示一行摘要，可展开（不复刻右栏完整视图 —— 那仍然交给「跳转会话」）。

**为什么**：截图里的右栏就是干这个的。有摘要在，房间不再是黑盒。

**代价**：中。需要在 `_emit` 旁路再挂一个观察器（已有 `_observe_room_frame`，复用即可），
注意**不能**进入会话热路径。

### 3.2 状态持久化

`MemberRuntime` 目前在内存，重启即丢。落盘到 `rooms-state.json`（或 rooms.json 的
`runtime` 段）：`state / started_at / queued / error`。

重启后：若该会话仍在跑 → 恢复 `running`；否则 `idle` 并标注「重启时状态未知」。

**代价**：低。但需要判定"会话是否仍在跑"的可靠依据。

### 3.3 失败重试

派发失败 → 自动重试 1 次（同一条消息，附带失败原因）。
仍失败 → 写入时间线，标记 `failed`，**不重试**（避免抖动时刷屏）。

失败分类（决定是否值得重试）：
- `目录不存在` / `会话已失效` → 不重试，提示用户修配置
- 连接类 / 超时 → 重试

**代价**：低。

## L4 成本与容量

### 4.1 成员级模型

`RoomMember.model / effort`，透传给 `_spawn(model=..., effort=...)`（该参数已存在）。

典型：advisor 用强模型，executor 用快模型，reviewer 用强模型。

**为什么**：现在所有成员用默认模型，"建议"和"执行"同价，成本没得控。

**代价**：低（`_spawn` 已支持）。UI 加两个下拉。

### 4.2 上下文预算

现在：自动带上最近 6 条**全文**，且与手动引用可能重复。

改为：
- **去重**：手动引用已包含的条目，不再进入自动上下文
- **预算**：自动上下文按字符数上限（默认 6000）从新到旧装填
- **有引用时自动降级**：存在手动引用 → 自动深度降到 2

**代价**：低。主要改 `_prompt`。

### 4.3 并发与排队可见

- `max_parallel` 做成房间字段（默认 2，上限 4）
- `RoomState` 增加 `waiting_reason`：`"等待并发额度"` / `"等待该成员上一回合"`
- 排队时 UI 显示原因，而不是只有「队列 · 1」

**代价**：低。

## 三、优先级与工作量

| 编号 | 内容 | 收益 | 工作量 | 建议 |
|---|---|---|---|---|
| L1.1 | 结构化产出 `cc-plan` | ★★★★ | 小 | **先做** |
| L3.2 | 状态持久化 | ★★★ | 小 | 先做 |
| L3.3 | 失败重试 + 分类 | ★★★ | 小 | 先做 |
| L4.2 | 上下文去重与预算 | ★★★ | 小 | 先做 |
| L2.1 | 成员角色 | ★★★★ | 小 | 第二批 |
| L2.2 | `advise_execute` 模式 | ★★★★★ | 大 | 第二批（核心） |
| L3.1 | 回合轨迹摘要 | ★★★ | 中 | 第二批 |
| L4.1 | 成员级模型 | ★★★ | 小 | 第二批 |
| L2.2b | `parallel_review` 汇总 | ★★★ | 中 | 第三批 |
| L2.2c | `roundtable` | ★★ | 中 | 按需 |
| L4.3 | 并发可见 | ★★ | 小 | 顺手 |

**建议先把「小工作量、高收益」的五项一次做完**（L1.1、L3.2、L3.3、L4.2、L4.1），
那会让房间立刻从"聊天室"变成"有结构的协作台"，而不必等大的模式改造。

## 四、明确不做（及理由）

| 不做 | 理由 |
|---|---|
| agent 之间全自动互聊（无人工干预的循环） | token 失控、互相附和、无法纠偏。`advise_execute` 保留人点「执行」这一步 |
| 跨房间记忆 / 全局知识库 | 引入检索与隐私问题，收益不明确 |
| 在房间内复刻完整右栏（工具流、diff） | 与「跳转会话」重复维护两套渲染，用摘要 + 跳转即可 |
| 自动 git 提交 / 自动合并 | 风险过高，必须人确认 |
| 房间级统一模型开关 | 与 L4.1 的成员级控制冲突，粒度太粗 |

---

## 五、验收标准（可测）

每项都要能落到测试或实测，避免"感觉变好了"：

1. **L1.1**：成员返回含 `cc-plan` 的文本 → 时间线出现卡片；不含 → 原样展示且不报错
2. **L1.2**：计划步骤指派给成员 → 派发文本等于该步骤文本
3. **L2.1**：advisor 的派发提示包含"产出计划"约束；executor 包含"逐步执行"
4. **L2.2**：`advise_execute` 下，advisor 回合结束**不自动**派发给 executor（等人点）
5. **L3.1**：一次含 2 个工具调用的回合 → `trace.tools` 计数正确，且不影响 TurnEnd 时序
6. **L3.2**：重启后 `running` 成员的界面状态与实际一致
7. **L3.3**：连接类失败重试 1 次；目录不存在不重试
8. **L4.2**：手动引用 3 条时，自动上下文降为 2 且不含已引用条目
9. **L4.1**：成员设了 model → `_spawn` 收到该 model

## 六、风险

- **提示词依赖模型服从性**：`cc-plan` 可能不被遵守 → 必须有"解析失败也正常展示"的兜底，
  且不因格式问题重试（会白烧 token）
- **结构化输出与流式展示的关系**：卡片应在回合**结束后**替换，而不是边流边解析
- **状态持久化的一致**：落盘与内存可能短暂不一致，以"会话实际状态"为准
- **角色提示词会改变现有行为**：需要在 `chat` 模式下保持完全向后兼容
